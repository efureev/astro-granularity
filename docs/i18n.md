# Strings

**English** · [Русский](./i18n.ru.md)

## Two kinds of strings, two mechanisms

**Package strings** — the labels inside design-system components (`Search…`, `Clear`,
`Close`). They come from `@feugene/fint-i18n` and are what this integration delivers.

**Application strings** — your headings, menu labels, body copy. They are none of this
integration's business. Plain objects resolved in `.astro` frontmatter and passed to
islands as props cost the client nothing and never appear in the snapshot.

Everything below is about the first kind.

## The pipeline

```
astro.config.mjs  →  virtual:granularity/i18n  →  ./app entrypoint  →  fint instance
                                                        ↑
                  middleware declares the route language before the page renders
                                                        ↓
                       snapshot of the rendered keys embedded into <head>
```

### The virtual module

Generated at config time from `i18n.packages` and `i18n.locales`:

```js
import { deriveI18nBlocks } from "@feugene/astro-granularity/runtime"
import { en as en0, ru as ru0 } from "@feugene/granularity/i18n"
import { en as en1, ru as ru1 } from "@feugene/granularity-chrono/i18n"

export const loaders = [en0, ru0, en1, ru1].flat()
export const blocks = deriveI18nBlocks(loaders)
export const defaultLocale = "en"
export const locales = ["en","ru"]
export const ssrStrings = "used"
```

Named imports rather than the `/i18n/all` aggregate — that is what lets the bundler drop
languages you did not ask for. With `locales: ['en','ru']` a package that also ships `es`
emits two chunks, not three.

### Where the route language comes from

`Astro.currentLocale`, read by the middleware **before** the page renders.

There is no other way. `@astrojs/vue` passes only `app` to the entrypoint, so the
component layer cannot know the route; and `injectScript` takes a string fixed once for
the whole build. Middleware is the single Astro channel that runs per page and knows
where it is.

Without an `i18n` block in `astro.config.mjs`, `Astro.currentLocale` is `undefined` and
the fallback is parsing the first path segment against `i18n.locales`. With that list
empty there is nothing to match, and the language is always `defaultLocale`.

### The snapshot

After the page renders, the middleware inserts a block before `</head>`:

```html
<script type="application/json" data-granularity-i18n>
{"locale":"ru","messages":{"ru":{"gr":{"pagination":{ … }}}},"blocks":{}}
</script>
```

The island entrypoint applies it **synchronously before `app.mount`**, which is possible
because `@astrojs/vue` awaits the entrypoint on both sides. The first client render
therefore already matches the server, and there is no flash.

Three decisions inside that block are not cosmetic:

- **`type="application/json"`, not an inline script.** The browser does not execute it, so
  `script-src` does not apply. A real inline script inserted from middleware could not be
  hashed — the page is already rendered by then — and would be blocked under
  `security.csp`.
- **Before `</head>`, not after `<head>`.** A kilobyte-sized snapshot inserted at the top
  would push `<meta charset>` past the first 1024 bytes, and the encoding starts being
  guessed.
- **Every `<` escaped**, not just `</script`. Inside a raw-text element `<!--` is a second
  way out.

## Snapshot modes

```ts
granularity({ i18n: { ssrStrings: 'used' } })
```

| Mode | In the HTML | The client |
| --- | --- | --- |
| `'used'` *(default)* | Only the keys the server rendered **on that page** | Fetches the dictionary in the background |
| `'full'` | The whole dictionary of the page language | Does not fetch it at all |
| `false` | Nothing | As if the feature did not exist |

Both are per page, not per site. The axis is "only what was rendered" versus "the whole
dictionary", and both are embedded into each page separately.

Measured on the example's overview page:

| | raw | gzip |
| --- | --- | --- |
| The page itself | 10 800 B | 3 064 B |
| `'used'` adds | **+366 B** (+3.4 %) | **+132 B** (+4.3 %) |
| `'full'` adds | +11 909 B (+112 %) | +3 945 B (+133 %) |

`'used'` keeps the dictionary a shared, cacheable chunk. `'full'` marks the block loaded,
so the chunk is never fetched — but a copy of the dictionary now sits in every page, on
the critical path of the document. For a multi-page site that is a loss twice over; for a
single landing page it is a win.

### Why `'used'` cannot make things worse

In `'used'` mode `blocks` stays empty, so nothing is marked as loaded and the client
still fetches the dictionary in the background. Anything the journal missed is healed
there. It is a best-effort improvement that cannot regress to worse than `false`.

### What `'used'` misses

Strings read through `tm()` — a subtree used as data: menu items, table columns. The
`onTranslate` hook does not fire for those, so they are absent from the snapshot and
arrive with the background fetch. `'full'` has no such gap because it takes the block
whole.

## Where the feature switches itself off

| Condition | Why |
| --- | --- |
| `output: 'server'` | Requests run concurrently in one process; the page state is a module-level variable, so one request's language could reach another's response |
| `build.concurrency > 1` | The same race, during the build |
| `i18n: false` | No loader module is generated at all |

The first two print a warning naming the fix. `ssrStrings: false` acknowledges the
decision and silences it.

## Client-side navigation

`ClientRouter` swaps the whole `<head>`, so the new page's snapshot is in the DOM — but
modules are not re-executed. Reading the snapshot once at module scope would leave the
live components rendering the first page's language while `<html lang>` and the snapshot
both say otherwise.

The entrypoint therefore re-reads it on every instance creation, and instances are keyed
by locale.

**When verifying this yourself, navigate through the router.** A `window.location.href`
assignment is a hard navigation: the document is fresh, so neither this nor the theme
defect reproduces, and a test built on it measures nothing.

## Instances

One instance **per page language**, not per island. Islands are independent Vue roots but
share a module graph, so in the browser there is always exactly one.

During the build the distinction matters: a prerender is a single process for the entire
build, so a single module-level instance would fix the language of the first page
rendered for every other page. Keying by locale is what prevents that.

## The seam for your own runtime

With `i18n: false` no middleware is registered and no snapshot is produced. The building
blocks are still exported from `./runtime` for an application that wants to assemble the
same pipeline over a different runtime:

| Export | Purpose |
| --- | --- |
| `readServerPageLocale()` | The route language declared during the build |
| `readSnapshotFromDocument()` | The snapshot out of the markup |
| `registerSnapshotBuilder(fn)` | Register who builds it |
| `SNAPSHOT_ATTR` | The attribute to look for |

Import them from `./runtime`, never from the root: the root entry runs in the Astro
config process, not in the prerender bundle, and its copy of the state is always empty.

See [recipe 6](./recipes.md#6-your-own-i18n-runtime) for the adapter side.
